BadgeMark（徽标标记） ​

按 badgeKey 查 bridge.badge 注册表，命中且未过期则给默认插槽内容挂绝对定位角标（包 ElBadge，不挤压主体）；未命中渲染裸插槽、DOM 逐字节不变。 范式页：apps/reference/src/pages/integration/badge/（7 场景）；生产驱动点见 MenuTree / MenuItemSub / AppHeader / ActionBtn 内部接入。

定位 ​

  • 何时用：自供 shell 自渲染导航、或业务自建的入口元素需要接徽标体系时
  • 何时不用：core 的菜单族与 ActionBtn 已内置接入，用它们时 [MUST NOT] 再自行包一层
  • opt-in 且零侵入：未 app.use(bridge) / key 未命中 / 标已过期 → 静默渲染裸插槽，[MUST NOT] 抛错
  • 完整契约（标记类型 / expireAt 失效 / key 约定 / 已知限制 / 为何不做冒泡聚合）见 bridge 文档 · 徽标注册表

快速上手（最小可用） ​

vue
<BadgeMark badgeKey="/order/list">
  <span>订单列表</span>
</BadgeMark>

app 侧往注册表写一条即出标：

ts
bridge.badge.set("/order/list", { kind: "new" });

能力边界 / 按需使用 ​

  • align 怎么选：看被包内容盒是否紧贴文字（不是看宿主类型）。
宿主.el-badge 盒高宿主高corner 落点core 用
ActionBtn14px（紧贴文字行）32px角标顶齐按钮顶，上溢 0corner 右上角
TabsHeader tab22px（紧贴）40px上溢 −1，不越界corner 右上角
菜单项 / AppHeader 模块条 / tile 卡片头50px（撑满整行）50px钉在行顶、上溢 9px 侵入上一行middle 垂直居中

差别根源：菜单项的 span 继承整行 line-height，.el-badge 盒跟着撑满一行，于是「内容顶边」≠「文字顶边」；按钮 / tab 的盒紧贴文字行，顶边即文字顶边。

  • [MUST NOT] 用 top: N% 或 ElBadge offset 魔数去凑：与字号 / 行高 / 主题 density 强耦合，一变就错位。盒紧贴文字的宿主用 corner，盒撑满行的用 middle。

硬约束：角标的出现 [MUST NOT] 改变宿主尺寸 ​

两档均为绝对定位，不占布局位。实测证据：同一批按钮打标前后逐项宽度差 全 0。

代价是绝对定位不占位 → 角标必然向右逃逸出宿主边界，逃逸量 = 角标宽 − 13px（EP 的 10px 内嵌已归零，另留 2px 让位；文字距按钮右缘 15px padding）：

内置标字数宽逃逸后果
新126px13px基本不碰邻居
更新 / 内测238px25px一般不碰邻居
开发中 / 规划中 / 待下线 / 未开通350px37px右缘可能顶到水平相邻宿主

⚠️ 原「内置标文案 [MUST] ≤2 个汉字」那条约束已作废（甲方 2026-09-19 明示「不用关心太长」）。 逃逸量最终由消费方的布局间距决定，core [MUST NOT] 声称能保证零重叠；文案长度的后果由布局承担。 core 自己的紧凑宿主照此办理：AppHeader 模块条各项首尾相接，挂标项按实测逃逸量补同宽右内边距（ii3dzw），本组件的绝对定位不变。 [MUST NOT] 因为这张表回推「所以该用图标 / 该截断」—— 见下文「内置档一律文字」。

⚠️ 那条作废管的是「别拿宽度回推去换方案」，不是「文案可以随便改长」（v0.32.0，b9tmkc）： 资讯三档回短是因为它们压根没被要求改过（撤回图标那批把悬浮气泡的 label 当正文搬了回来）， 逃逸量降回去只是顺带。状态四档三字照旧合法。

尺寸：固定 12px / 18px，不随 density 变 ​

项值来源

pill 高18px--el-badge-size

实测按钮 / tab / 菜单三处完全一致，文字在 pill 内垂直居中偏移均为 0（三处 line-height 虽不同——按钮 12px、tab 16.8px、菜单 56px 继承整行行高——但 pill 是 inline-flex + align-items:center + 固定高，不产生偏移）。

⚠️ 不随主题 density 缩放：core 的 THEME_FIELD_SPECS 只往 :root 挂变量且未映射任何 badge 变量，故 density 档（compact / cozy / comfortable）不改角标尺寸。这是刻意的——角标应恒为全局最小号，跟着 density 缩放可能小到不可读。消费方要改自行覆盖 --el-badge-font-size / --el-badge-size。

🔴 内置档一律文字，[MUST NOT] 再改图标 ​

甲方 2026-09-19（附菜单实拍图）：「badge 的图标撤掉，还是直接展示文字，两个字就是两个字、 三个字就是三个字（不用关心太长）」。图标态在真实菜单里是一排看不懂的小圈。

原「≤2 汉字」的宽度约束随之作废 —— 它当初的依据是「三字宽 50px、逃逸 36px 会压到水平 相邻宿主」，而甲方明确说不用关心太长。⇒ 实施方 [MUST NOT] 拿那条依据回推「所以还是该用 图标」，也 [MUST NOT] 自行折中（截断 / 省略号 / tooltip 代文字）—— 那是用没被授权的方案 绕过已下达的决定。逃逸的代价由消费方的布局间距承担，core 照旧不声称能保证零重叠。

⚠️ 这不是「把 v0.30 revert 掉」：状态四档（wip / planned / deprecated / locked） 在 ≤v0.29 时本来就是图标，本次是它们首次以文字出现。三档是新的一致态：

版本资讯三档 new/updated/beta状态四档 wip/planned/deprecated/locked
≤ v0.29文字（新 / 更新 / 内测）图标
v0.30图标图标
v0.31.0文字，但文案被夹带改长（新上线 / 已更新 / 内测中）文字

⚠️ 形态本身在传达分类：资讯档短（1–2 字）、状态档三字 —— v0.31.0 那一版七档全三字，扫视时分不出两类。

图标是全族退场：ElIcon / ElTooltip / 预设的 icon 与 iconScale 字段一并删除。 悬浮气泡随之去掉 —— 它当初存在只为「语义随文字消失后补回来」，文字回来了它就是重复。

展示开关：逐条 visible + 全局默认 ​

徽标当初是拿来做新手引导的；有了 forge-plugin-guide 之后，徽标不再必须显示。

层写法默认
逐条bridge.badge.set(key, { kind: "new", visible: false })undefined = 跟随全局
全局createCoreBridge({ badge: { defaultVisible: false } }) 或 bridge.badge.setDefaultVisible(false)true（展示）

逐条显式值恒优先于全局默认（与本仓所有 config-hook 同口径）。 全局默认取 true 是为了不改变现有下游观感；把它关成不展示是消费方的选择。

🔴 「配置了但不展示」与「没配置」是两回事 ​

注册表DOMdata-dc-badge-key引导能否定位
没配置无 entry渲染裸插槽（无 ElBadge）❌ 无❌
配置了但不展示有 entry渲染 ElBadge，角标被藏✅ 在✅

⇒ 隐藏 [MUST NOT] 用 v-if 掉整个 ElBadge —— 那会连挂点一起没掉， forge-plugin-guide 当场失去锚点。把徽标全部设为不展示时，引导仍能正常串出并定位。

藏法 = 0 尺寸 + overflow:hidden + 事件屏蔽（甲方裁定） ​

less
width: 0; height: 0; min-width: 0; padding: 0; border-width: 0;
overflow: hidden; pointer-events: none;

文字仍在 DOM 里但被裁掉，故 [MUST] 同时给 aria-hidden="true"（0 尺寸只是视觉裁掉， 读屏照念）。

🔴 [MUST NOT] 用 display: none，也 [MUST NOT] 沿用 ElBadge 的 hidden prop （它内部就是把 sup 从布局里摘掉）。理由不是「保住锚点」—— 那是错的因果： data-dc-badge-key 挂在 ElBadge 根元素（包着宿主内容的 wrapper，有真实尺寸）上， 不是那个十几 px 的 pill，两种藏法都不断锚。

真正的理由是「仍然占位可测」：display:none 的元素 getClientRects().length === 0， 而这正是 plugin-guide/src/anchor.ts 的可见性判据（以及 kq2m8w 引导整页卡死 P0 的成因） 所依赖的那条线。保持「0 尺寸但仍在布局里」，可以让任何按 rect 判可见性的下游逻辑 不被隐藏态坑到。

🔴 遮挡档（locked）拒绝隐藏 ​

BADGE_MASK_KINDS（现仅 locked）不接受隐藏：逐条 visible: false 对它无效， 全局默认的「不展示」也不作用到它；dev 下会 console.warn 一句（静默忽略 = 消费方 以为设了其实没设）。

依据：遮挡是功能不是资讯。藏了会落进两种更坏的形态之一 —— 「隐藏了但仍然挡」⇒ 用户看到一个点不动又没有任何说明的按钮； 「隐藏了就不挡」⇒ 未开通的功能变成可点，功能性回退。

anchor：只要挂点、不要角标 ​

想给某个菜单项 / 按钮做新手引导，但它本身没有「新 / 更新」之类的标要显示时用它。 [MUST NOT] 为此硬挂一个 new —— 那会在界面上多出一个用户看不懂的角标。

与 visible: false 的关系（[MUST] 按此口径，[MUST NOT] 留两套说法）：两者都保留，语义不同。

语义藏法
kind: "anchor"「这里本来就没有标」—— kind 无资讯语义 + 恒隐藏同一套
visible: false「有标（new / beta / …），只是此刻不显示」同一套

⇒ anchor 不是新开关的语法糖：它已是发布契约，且语义是「无标」而非「有标先不显示」。 两者共用同一套藏法（0 尺寸 + overflow:hidden + 事件屏蔽）， [MUST NOT] 让它继续走 ElBadge 的 hidden —— 那就是「两种隐藏机制」。

遮挡：只有 locked 一档拦点击 ​

挂 locked 的宿主会被铺一层透明遮罩吃掉点击，同时打 tabindex="-1" + aria-disabled="true"（移出 Tab 序列，但读屏仍能读到该项并报告为不可用 —— 「未开通」是要让用户知道存在且可申请的功能，不是要藏起来）。

其余全部 kind 照常可点，含 wip：开发中 ≠ 不可达 —— 半成品页面让人点进去看是 正常预期，而未开通是权限边界，才必须拦。

点击被拦时走 entry.onTrigger；未配则出默认提示「请联系平台开通功能」。 ⚠️ onTrigger 只在拦得住时才有触发点 ⇒ 给 wip 配它不会被调用。 要拦某项就改挂 locked，[MUST NOT] 指望用 onTrigger 把可点档变成不可点。

反模式 / 注意 ​

  • custom 传色值字面量：type [MUST] 取语义档（primary/success/warning/danger/info），写死色跨主题不响应（规则 14）
  • 包纯文字却用默认 corner：角标会悬在文字上方并溢出相邻行
  • 指望它做聚合：本组件只按 key 查表渲染，core [MUST NOT] 把子级的标上卷到父级；聚合由 app 自算后往父级 key 写 entry
  • 以为角标是实心底白字：已改镂空（见下节）。旧描述作废，[MUST NOT] 照旧假设
  • 以为内置档是图标 + 气泡：v0.30 那一版的形态，本版已全档改回文字，气泡随之去掉
  • 拿 v-if 藏徽标：会连 data-dc-badge-key 挂点一起没掉，引导插件当场定位不到；隐藏一律走 visible
  • 给 locked 配 visible: false：无效（遮挡是功能不是资讯），dev 下有 console.warn

镂空（outline）观感 ​
